# Architecture

## Стек

- pnpm-монорепо: `apps/api` (Fastify 5, better-sqlite3, SimpleWebAuthn, zod), `apps/web` (Vue 3, Vite,
  Pinia, vue-router, vite-plugin-pwa), `packages/shared` (разделы, уровни, zod-схемы, типы ответов).
- TypeScript 6 (не 7: vue-tsc опирается на JS API компилятора). `shared` подключается исходниками (`.ts`),
  отдельной сборки нет.
- api в образе — один бандл esbuild (`apps/api/build.mjs`); снаружи бандла только нативный better-sqlite3.
- БД — один файл SQLite `/data/money.db` (WAL). SQL написан руками в `apps/api/src/store.ts`, без ORM.

## Путь запроса

```
телефон → домен приложения
  → HTTPS-прокси (свой или caddy-docker-proxy)
  → money-web-1:80 (nginx: фронт + /api → api:3000)
  → money-api-1:3000 (Node, /data = каталог MONEY_DATA)
```

Способ доступа — оверлей compose: `docker-compose.port.yml` или `docker-compose.caddy-proxy.yml`. Настройки
конкретной установки — в `deploy/.env` и `deploy/money.env` (вне git). Один origin для фронта и API — passkeys
и cookie без CORS.

## Вход

- Только passkeys (WebAuthn, discoverable). Паролей нет.
- Регистрация только по инвайту. Первый инвайт — из консоли сервера (`scripts/invite.sh`), первый
  зарегистрированный становится админом (`users.admin`).
- Сессия — случайный токен в cookie `sid` (httpOnly, Secure, SameSite=Lax), в БД — sha256. 90 дней,
  скользящий срок.
- CSRF: изменяющие запросы принимаются только с `Origin = ORIGIN` (хук в `app.ts`).
- Незавершённые церемонии WebAuthn — таблица `challenges`, id в cookie `wa`, одноразовые, 5 минут.

## Модель доступа

- Каждый пользователь — своё изолированное пространство (траты, план, списки — всё с `owner_id`).
- Разделы: `shopping`, `transactions`, `incomes`, `summary`, `plan` (`packages/shared`). Уровни: `view`, `edit`.
- Таблица `grants (owner_id, member_id, section, level)`. Нет строки = нет доступа. Владелец видит своё целиком.
- Доступ выдаётся инвайтом с набором прав. Новый человек по нему регистрируется, существующий — принимает.
  Принятый инвайт **заменяет** права от этого владельца целиком.
- Владелец меняет права участника или закрывает доступ; участник может отказаться сам.
- Инвайт без разделов (= просто новый аккаунт на сервере) может создать только админ.
- `summary` без `transactions` — итоги по категориям без отдельных трат: эндпоинты сводки не должны
  отдавать строки трат.
- `summary` без `incomes` — только расходы: сервер не отдаёт доходы, остатки, начальный остаток и виды
  поступлений (`withoutIncome`), менять начальный остаток нельзя.

## Покупки (этап 2)

- Таблицы `shopping_lists`, `shopping_items`, `shopping_history` (миграция 2). Эндпоинты —
  `/api/spaces/:owner/shopping/...`, доступ через `requireSection` (`apps/api/src/access.ts`).
- id списков и позиций создаёт клиент: PUT идемпотентен, повтор из офлайн-очереди не плодит дубли.
- Удаление — пометка `deleted_at` (надгробие): запоздалое изменение из чужой очереди не воскресит позицию.
  Конфликты — «последняя запись выигрывает».
- Первый заход в пространство создаёт список «Продукты»; последний список удалить нельзя.
- Подсказки при вводе — из `shopping_history`, **свои у каждого списка** (миграция 4 разложила старую общую
  историю по спискам из позиций). Исправили опечатку в названии — подсказка переезжает на новое название;
  ненужную подсказку убирают крестиком (`DELETE .../suggest?list=&name=`), позиции это не трогает.
- У позиции необязательная стоимость (`price`, копейки, миграция 5): правится в строке, под списком — итог
  к покупке, в заголовке «Куплено» — итог купленного. PUT без `price` цену не трогает (старые клиенты и
  офлайн-очереди), `null` — убирает.
- Купленное не зачёркивается (видно по галке), над ним — поиск (без учёта регистра и «ё»). Править можно и купленную
  позицию. Если количество начинается с числа, в правке есть «Цена за 1»: сумма = число × цена
  (`apps/web/src/qty.ts`, `components/ShoppingItemEdit.vue`). Хранится только сумма; «по 73 ₽» под ней — для 2–99 штук.
- Удаление позиции — свайп влево (`components/SwipeRow.vue`); кнопки «Очистить купленное» в интерфейсе нет
  (эндпоинт `clear-checked` оставлен: в офлайн-очередях телефонов могли остаться такие операции).

### Живые обновления и офлайн

```
изменение → PUT → store → bus.publish(owner, 'shopping', событие)
                            └→ каждому подписчику SSE /api/spaces/:owner/shopping/events
                               (права перепроверяются на каждой отправке; закрыли доступ — поток рвётся)
```

- `apps/api/src/bus.ts` — шина в памяти (один процесс api). Сервер шлёт `{"type":"ping"}` каждые 20 с.
- Клиент (`apps/web/src/stores/shopping.ts`): правка сразу видна на экране и ложится в очередь в
  localStorage, очередь отправляется по порядку. Нет сети — повтор каждые 5 с и по событию `online`.
  4xx — операция выбрасывается, список перечитывается с сервера.
- Последний снимок списка лежит в localStorage — список открывается без сети. При выходе кэши стираются.
- «Нет связи» показывается, только если связь пропала (ошибка запроса/потока — флаг `offline`) и не вернулась
  за 2,5 с. Подключение потока при открытии раздела — не обрыв.
- Переподключение: сам EventSource (обрыв сети), свой таймер (ответ-ошибка), сторож 50 с без событий
  (полуоткрытое соединение), возврат приложения на экран (iOS усыпляет PWA в фоне).

## Траты, поступления, план (этап 3)

- Миграция 3: `categories` (один уровень подкатегорий через `parent_id`), `income_kinds`, `transactions`,
  `incomes`, `plan_items` + `plan_item_categories`, `space_setup` (шаблон справочников заведён).
- SQL — `apps/api/src/store-money.ts`, эндпоинты — `apps/api/src/routes/money.ts`.
- Суммы — целые копейки; даты — строки `YYYY-MM-DD` по календарю пользователя; месяц — `YYYY-MM`.
- Права: траты — `transactions`, поступления и их виды — `incomes`, план и категории — `plan`.
  Справочники (`/dictionaries`) читаются с доступом к любому из transactions/incomes/summary/plan.
- Справочники при первом заходе заполняются шаблоном (Продукты, Бытовые, Авто, Коммуналка,
  Связь/Интернет; Зарплата, Аванс, Кэшбек, Прочее) — один раз, удалённое не возвращается.
- Удаление категории/вида — архив: старые записи сохраняют название, новые в архивную нельзя.
  Старую запись с архивной категорией править можно, если категорию не менять.
- **Статья плана = одна категория верхнего уровня** (на категорию — одна статья, название всегда из неё).
  Удалили категорию — статья уходит с ней. Экран категорий — «Ещё → Категории» (право правки — раздел `plan`).
- **В плане только известные ежемесячные траты.** `plan_item_parts` (миграции 7–8) — подкатегории, которые входят
  в статью; остальные подкатегории и траты прямо в категории считаются «вне плана». Нет ни одной строки — статья
  на всю категорию. Сумма строки 0 — подкатегория входит в общую сумму статьи; есть хоть одна сумма — итог = их
  сумма. PUT без `parts` набор не трогает, `[]` убирает. Удалили подкатегорию — строка уходит, сумма пересчитывается;
  если расписанных сумм не осталось, сумма статьи остаётся последней.
- **Подкатегория при вводе траты обязательна**, если у категории они есть (проверяет и API). Старую трату,
  записанную прямо в категорию, можно править, не меняя категорию; в сводке она — «без подкатегории».
- **План прошедших месяцев зафиксирован** (`plan-history.ts`, миграция 9). Перед первой правкой плана или
  категории в новом месяце текущий план пишется в `plan_versions` как действующий по прошлый месяц включительно.
  Сводка за месяц берёт ближайшую версию не раньше него, иначе текущий план. Факт считается по настоящим тратам:
  запись задним числом меняет факт прошлого месяца, но не его план. Смена месяца — по `TZ` контейнера api.
- Траты и поступления пишутся только онлайн (без офлайн-очереди, в отличие от покупок).

## Сводка (этап 4)

- `GET /api/spaces/:owner/summary?month=` (раздел `summary`) — только итоги, без строк трат: её видит и тот,
  кому «Траты» не открыты. SQL — `apps/api/src/store-summary.ts`.
- «Остаток» в «Сводке» и в «Тратах» — одно число: остаток на начало + поступления − траты месяца.
- **Остаток на начало** = начальный остаток (`space_settings`, миграция 6; задаётся на «На начало», право
  `summary: edit`) + поступления − траты с его месяца. Без начального остатка — от самых первых записей.
  Для месяцев раньше начального остатка — `null` («—»).
- **План-факт**: факт статьи = траты выбранных подкатегорий (если не выбраны — всей категории). «Вне плана» — всё
  остальное.
- **Динамика** — 6 месяцев по выбранный. График `components/HistoryChart.vue`: столбики на одной оси,
  цвета — категориальные слоты 1–2 (синий/оранжевый), проверены валидатором dataviz в обеих темах; легенда,
  подсказка по нажатию, таблица цифр.
- Метры план-факт: синий; ≥ 90 % — жёлтый; > 100 % — красный со значком и словом «перерасход».

## Фронт

- Вкладки: Покупки · Траты (траты + поступления) · Сводка · План · Ещё (`apps/web/src/tabs.ts`).
  Вкладка видна, если в текущем пространстве есть доступ хотя бы к одному её разделу.
- Переключатель пространства «Моё / <владелец>» в заголовке страницы; выбор хранится в localStorage.
- Обновление PWA — `src/pwa.ts` (см. gotchas). Номер версии (ревизия коммита) — внизу экрана «Ещё».
- Плотная шкала шрифтов: основной текст 15 px, строки списков ~40–42 px. Поля ввода — не меньше 16 px
  (иначе Safari на iPhone увеличивает страницу при фокусе).
- Оформление — свои токены `apps/web/src/styles/tokens.css` в системном стиле iOS: тёмная тема по
  умолчанию, светлая по системе или вручную, акцентный цвет на выбор.

| `apps/api/src/cli.ts` | консоль сервера: invite, users, backup |
| `apps/api/test/authenticator.ts` | программный passkey для тестов (настоящая проверка SimpleWebAuthn) |
| `apps/web/src/stores/session.ts` | кто вошёл, чьё пространство открыто, права |
| `deploy/` | Dockerfile (targets api и web), nginx, compose с оверлеями, образцы настроек `*.example` |
